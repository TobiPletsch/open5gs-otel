# 10. Metrics with the OTel SDK (branch `otel-metrics`)

**Status:** implemented on branch `otel-metrics` and deployed as image
`55f9dd197`. `otel-poc` stays the fallback.

## What it adds

The SMF records every PDU session establishment attempt with the
OpenTelemetry metrics SDK. These metrics are in addition to the existing
Prometheus counters, which are unchanged:

| Metric | Type | Attributes | Recorded |
|---|---|---|---|
| `open5gs.smf.pdu_session.establishment.attempts` | Counter (`{attempt}`), delta | `5gs.outcome`, `error.type` (`none`, `5gsm_cause_<n>`, `http_<n>`, `aborted`), `5gs.dnn` | Where the `smf.pdu_session.establishment` span ends |
| `open5gs.smf.pdu_session.establishment.duration` | Histogram (ms), delta | `5gs.outcome` | Same place |

* **Export.** Every 10 s via OTLP/HTTP to the same endpoint as the traces
  (`OTEL_EXPORTER_OTLP_ENDPOINT`). No extra configuration is needed.
* **Storage.** The agent's metrics pipeline already accepts OTLP. The data
  lands in ClickHouse `otel_metrics_sum` and `otel_metrics_histogram`.

## Dashboard "Otel Poc - Metrics, Traces and Logs"

Generated by `docker/otel-poc/grafana/gen_dashboard_metrics.py`. It contains
the light dashboard (imported from `gen_dashboard_light.py`) with a metrics
section on top:

* **Failed attempts by cause** (bars per `${bucket}` s). Clicking a bar sets
  `cause` + `bucket_start`.
* **Attempts by outcome**, **duration** (average/maximum), and a **cause
  table**. Clicking a cause sets `cause` for the whole time range.
* **Failing traces table.** It shows SMF spans with `outcome != success`,
  filtered by cause, by the UE search and by the **exact window of the
  clicked bucket's data points** (`min(StartTimeUnix)` … `max(TimeUnix)`).
  The window is exact because each delta data point covers one export
  interval and the counter is incremented where the span ends.
  * Verified on 2026-11-18: buckets with counter values 444 / 590 / 191 gave
    exactly 444 / 590 / 191 traces.
* **Below:** the UE search, registration blocks, trace and logs, exactly as in
  the light dashboard. All links keep the metric selection.

## Limits

* **Only failures that reach the SMF.** Requests rejected earlier by the AMF
  (e.g. unknown DNN, rejected with a 5GMM status) have no SMF span and no SMF
  metric. Counting them needs AMF instrumentation at the point where the
  request arrives.
* **No exemplars.** opentelemetry-cpp exports no exemplars yet, so the link
  from metric to trace runs through shared attributes and the time window
  (see [09](09-exemplars.md)).
